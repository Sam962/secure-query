Scope: full read of every `.py`, config, prompt, test, CI, Docker, UI and doc file
(not read: `docs/DEMO.md`, `docs/OWNERSHIP.md`, `docs/baselines/*`, suite/golden JSON,

Tags: **[V]** verified by execution or by reading the exact lines cited;

Context: the project is moving from a local Qwen 7B (Ollama) to the OpenAI API

## Verdict

**Solid security core, risky product surface, over-engineered in breadth.**
The kernel (catalog → validate → sqlglot AST compile, or SQL → qualify → rewrite) is
good and the adversarial tests are real. Around it sit two planner paths, three
execution backends, three metric kinds, a builder DSL, a 788-line regex guard layer and
a Chinook-specific demo package that production code imports.

| Dimension | Score | One sentence |
|---|---|---|
| Correctness | 6 | Core compile/validate is right, but the UI executes a *different* plan than the one the user reviewed, and the type/ordering rules reject plans a competent model will produce (`Total > 5`, trend sorted by month). |
| Security | 7 | SQL surface is well locked down (allowlists, AST-only, `read_only=True`, row filters through approved paths); weak points are operational: audit log stores raw questions, DB error text leaks to clients, Postgres/Databricks read-only is assumed not enforced. |
| Performance | 5 | Catalog, principal registry and OpenAI client are rebuilt per request; DuckDB connection + thread pool per query; timeouts don't cancel; SDK retry × app retry can block a worker for minutes. |
| Simplicity | 4 | Two planners, three backends, three metric kinds, builder DSL, heuristic guards, retrieval, suggestions, self-consistency, adjudication — for an 11-table demo and a 12-case holdout. |
| Maintainability | 6 | Good module split and tests, but ~8 duplicated logic blocks, demo→production import direction, string-coupled error codes, and a stale `.venv` that cannot import the package. |

## Findings

### Critical

#### C1. Confirm → Run executes a re-planned query, not the reviewed one. [V]

`src/secure_query/api/static/index.html:548` calls `/ask/confirm` with `{question}`;
`:559` calls `/ask` with `{question, execute:true}`. `api/http.py:170-176` only forces
`confirm_only`. `api/service.py:146-163` calls the LLM again. Nothing sends `plan_hash`
back or pins execution to it. With temperature > 0, retrieval, or model nondeterminism
the user approves SQL A and runs SQL B. That voids the "review before run" guarantee the
UI advertises (`index.html:515` shows the hash as if it mattered).

Fix: make execution take the reviewed artifact, re-validate it (no LLM), and run.

```python
# http.py
class ExecuteRequest(BaseModel):
    plan_hash: str
    plan: dict | None = None   # LQP path: plan JSON returned by /ask/confirm
    sql: str | None = None     # SQL path: validated SQL returned by /ask/confirm

@app.post("/ask/execute")
def ask_execute(req: ExecuteRequest, principal=Depends(_principal)):
    config = get_runtime()  # cached, see H4
    scoped = catalog_for_principal(config.catalog, principal)
    if req.plan is not None:
        plan = inject_row_filters(LogicalPlan.model_validate(req.plan), principal)
        compiled = validate_and_compile(normalize_plan(plan, scoped), scoped)
    else:
        compiled = validate_sql(req.sql, scoped, row_filters=principal.row_filters)
    if compiled.plan_hash != req.plan_hash:
        raise HTTPException(409, "reviewed plan no longer matches")
    return execute_compiled_query(compiled, config, principal=principal, ...)
```

Return `plan`/`sql` from `/ask/confirm` (service already holds `plan` and `compiled`
at `service.py:241-251`). The UI stores them and posts them back. No server-side state.

### High

#### H1. Integer literal on a float column forces a repair round-trip. [V]

Probe: `{"op":"gt","column":Invoice.Total,"value":{"type":"integer","value":5}}` →
`typecheck.literal_mismatch` from `kernel/validate.py` `_LITERAL_TO_DTYPE`;
`{"type":"float","value":5}` is rejected by Pydantic at `kernel/logical_plan.py:41-95`
(JSON `5` parses as `int`). Only `5.0` passes. Any "Total > 5" costs a second LLM call,
and if the repair also writes `5` the question fails.

Fix: `_LITERAL_TO_DTYPE["integer"] = {"int", "float"}` and in `LiteralValue` coerce
`int → float` when `type == "float"`. Add the probe as a test.

#### H2. Trend plans cannot be ordered by their time bucket. [V]

`validate.py:194 _check_dead_order_keys` emits `plan.order_key_not_grouped` for
`order_by Invoice.InvoiceDate` when the bucket is in `time_buckets`, not
`group_by.columns`. "Monthly revenue over time" naturally orders by month; the model
must omit `order_by` or sort by alias, else a repair. `SYSTEM_PROMPT` doesn't say so.

Fix: treat `tb.column for tb in plan.group_by.time_buckets` as grouped keys in
`_check_dead_order_keys`, and compile `ORDER BY` to the bucket expression.

#### H3. List intent through a child-table filter duplicates parent rows and projects every joined column. [V]

Probe: `source=Customer`, filter `Invoice.BillingCountry='USA'`, no explicit select →
`SELECT <all Customer cols>, <all Invoice cols> FROM Customer INNER JOIN Invoice …
LIMIT 500` → 91 rows for 13 distinct customers. `kernel/joins.py fan_out_errors` only
guards aggregates; `validate.py` has no rule for non-aggregated plans.

Fix: for plans with no aggregations, when a joined table is on the many side relative to
source, either project only source columns + `SELECT DISTINCT`, or compile the child
filter as `EXISTS (…)` the way `sql_validate._inject_row_filters` already does
(`_exists_through`). Prefer the EXISTS rewrite; it is already written.

#### H4. Per-request construction of catalog, principal registry and LLM client. [V reading, I cost]

`api/http.py:99,108,135` call `runtime_config()` which reloads/validates the catalog
from disk each time (`engine/runtime.py:70`); `auth/__init__.py:113` reloads the
principals JSON on every `resolve_principal`; `service.py:153/162` build
`default_client()` → `OpenAI(...)` per ask (`planner/llm.py:60`), losing the SDK
connection pool. With `SECURE_QUERY_PROVIDER` unset, `resolve_llm_settings` also probes
`localhost:11434` (`llm.py:254,268,307`) per request.

Fix:

```python
@functools.lru_cache(maxsize=1)
def get_runtime() -> RuntimeConfig: return runtime_config()
@functools.lru_cache(maxsize=1)
def get_client() -> LLMClient: return default_client()
@functools.lru_cache(maxsize=1)
def get_registry() -> dict: return load_principal_registry()
```

Expose `cache_clear()` for tests. Hot-reload via mtime check if wanted, not per request.

#### H5. OpenAI client has no timeout/max_tokens, and retries compound. [V reading]

`llm.py:56-60` constructs `OpenAI(api_key=…, base_url=…)` only — SDK defaults are 600s
timeout and `max_retries=2`. Around that, `_complete` loops 5× on `RateLimitError` with
`time.sleep(15)` (`llm.py:12-13, 81-102`), and `except Exception` at `:85-91` retries
*any* non-429 error once more without `response_format` (an `AuthenticationError` or
400 is sent twice). Worst case one `/ask` blocks a Starlette worker for many minutes;
`max_repairs=1` doubles it. No `max_tokens` means a runaway completion is billed in full.

Fix:

```python
self._client = OpenAI(api_key=..., base_url=..., timeout=30.0, max_retries=2)
create_kwargs = {..., "max_tokens": 1200, "seed": 7}
# drop the app-level RateLimit loop and the blanket response_format fallback
# for provider == "openai"
```

#### H6. `_check_fan_out` is skipped entirely when any join side is derived. [V reading, I exploit]

`kernel/sql_validate.py:369-382` returns `[]` for the whole scope if a CTE/derived table
participates. A model (or a prompt-injected question) can write
`WITH i AS (SELECT * FROM Invoice) SELECT c.Country, SUM(…) FROM Customer c JOIN i …`
and the sum-over-fan-out check is bypassed. Same at `:309`, where a derived side is
marked `approved = True` for join-path checking.

Fix: resolve each CTE to its base-table grain (CTE scopes are already validated
individually; record `scope → (base tables, group keys)`) and run the grain check
against that, or refuse aggregates over joins with derived sides unless `allow_any_join`.

#### H7. Postgres/Databricks read-only is not enforced in code. [V]

`engine/postgres.py:138-140` sets `autocommit=True` and `statement_timeout`; nothing
sets `default_transaction_read_only`. `databricks.py:234` docstring: "read-only grants
assumed". `execute.py:171` does pass `read_only=True` to DuckDB. The SQL validator is the
only barrier for the two production backends.

Fix: `conn.execute("SET default_transaction_read_only = on")` after connect; for
Databricks, document that the warehouse principal must be `SELECT`-only and check
`SHOW GRANTS` at `/ready`.

### Medium

#### M1. Audit JSONL stores the raw question, SQL and plan. [V reading]

`engine/execute.py:39-66 AuditRecord` + `_maybe_write_audit`. Questions contain
whatever users type. Replace `question` with `sha256(question)` + length; keep
`plan_hash` and SQL.

#### M2. DB error text returned to clients; `PlannerError` unhandled; `/ready` leaks tenant. [V]

`api/http.py:154-155` → `HTTPException(503, detail=str(exc))`. DuckDB/psycopg messages
include table/column names and sometimes file paths. `PlannerError` has no handler →
500 with traceback in logs. `/ready` (`http.py:103-115`) is unauthenticated and returns
`catalog_tenant`.

Fix: generic client message + audit id, log detail server-side; add `PlannerError`
handler → 502; strip tenant from `/ready` or require auth.

#### M3. Timeout does not cancel the query. [V reading, I behaviour]

`execute.py:172-181` (same in `postgres.py:141-152`, `databricks.py:257-297`):
`ThreadPoolExecutor(max_workers=1)`, `future.result(timeout)`, then
`pool.shutdown(wait=False)` and `_safe_close(con)`. The worker keeps running; closing a
DuckDB connection with an in-flight query from another thread is undefined.

Fix: `con.interrupt()` before close on DuckDB; for Postgres rely on `statement_timeout`
(already set) and drop the thread pool.

#### M4. `_COMPILE_CACHE` is an unlocked module-global `OrderedDict`. [V reading, I race]

`kernel/compile.py:43-99` does `get/move_to_end/[]=/popitem` from FastAPI's threadpool.
Wrap with `threading.Lock` or use `functools.lru_cache` on a pure
`(plan_json, catalog_hash, dialect) → CompiledQuery` function.

#### M5. Prompt size and caching. [V sizes]

LQP: `SYSTEM_PROMPT` ≈ 6.4k chars (~1.6k tokens) + catalog summary ≈ 4.5k chars
(~1.1k tokens) → ~2.8k input tokens per attempt; SQL path ~1.4k. Order is system →
catalog → question, so the prefix is cacheable *as long as the catalog text is
identical* — but `retrieve.py` (auto k=8 when >16 tables, join-hop expansion) rewrites
the catalog block per question and defeats OpenAI prompt caching exactly when catalogs
are large.

Fix: emit the full catalog as the stable block and append a short "likely relevant
tables: …" line after it; only truncate when the full summary exceeds a token budget.
Trim `SYSTEM_PROMPT` once structured outputs (M6) carry the shape.

#### M6. Use structured outputs instead of `json_object` + prose. [V reading]

`llm.py:79` uses `{"type":"json_object"}`; the IR is already a Pydantic model.
`response_format={"type":"json_schema","json_schema":{"schema":
LogicalPlan.model_json_schema(), "strict": True}}` (or
`client.beta.chat.completions.parse(response_format=LogicalPlan)`) removes a class of
repair calls (`JSONDecodeError`, missing fields, the `joins` key popped in
`planner/plan.py`). Note: strict mode disallows `str | int | float` unions in
`LiteralValue.value` — represent the value as a string and coerce by `type`.

#### M7. Heuristic guards cost more than they save on the new model. [V from `docs/STATUS.md`]

`planner/guard.py` (788 lines) — STATUS reports `dropped_concept` stopped 11 wrong
answers and blocked 32 right ones with gpt-4.1-mini. `_STOP_WORDS` (`guard.py:57-180`)
has duplicate entries (`"every"` 69/132, `"each"` 70/148, `"either"` 103/145,
`"appear"` 121/143/163); `catalog_vocabulary` (`:643`) is recomputed per guard call.

Fix: gate each guard behind the holdout; keep only those with
`blocked_wrong > blocked_right`; make the set configurable per catalog; memoize
`catalog_vocabulary(catalog)` keyed on catalog hash.

#### M8. SQL path prompts DuckDB SQL for every backend. [V reading, I failure]

`planner/sql_plan.py:28` and `kernel/sql_validate.py:83` parse as `duckdb` and emit
`catalog.sql_dialect`. `strftime`/`date_part` (whitelisted in `_SAFE_ANONYMOUS :51`)
have different semantics on Postgres and Databricks.

Fix: prompt with `catalog.sql_dialect` and parse with the same.

#### M9. `MockLLMClient` cannot serve the SQL path. [V]

`llm.py:154` keys on `"User question:\n"`; `sql_plan.py:53` writes `"Question:\n"`. The
mock holdout gate in CI therefore only exercises the LQP path even when
`SECURE_QUERY_PLANNER=sql` — the path STATUS says is better (68.8% vs 52.2%).

#### M10. `_enforce_limit` caps only the outer query. [V reading]

`sql_validate.py:433`: a CTE `SELECT * FROM Invoice` has no limit and materializes the
whole table before the outer LIMIT. Fine on DuckDB, expensive on a warehouse. Push the
limit or refuse unbounded CTEs over large tables.

#### M11. Dev environment is broken; CI masks it. [V]

`.venv` editable install is `secure-query 0.1.0` with
`MAPPING={'secure_query': '…/secure-query/secure_query'}` (pre-`src/` layout; commit
`3153059` moved it). `python -c "import secure_query"` in the repo venv fails; `pytest`
errors on collection. CI does a fresh install so it passes.

Fix: `pip install -e '.[dev,planner,api]'`; add `python -c 'import secure_query'` to a
`make check`.

#### M12. `import secure_query` imports FastAPI. [V]

`src/secure_query/__init__.py` → `api.service` → `api/__init__.py` → `http` →
FastAPI/Starlette loaded. `docs/ARCHITECTURE.md` claims core = pydantic + sqlglot.
Remove the re-export or lazy-import.

## Simplify

**Delete**
- `kernel/builder.py` — used only in tests/demo; `aggregate/rank/compare/filter_and_list`
  return the same builder, `compare` ignores `right`.
- `planner/suggest.py`, `api/respond.money_scale_note` — Chinook-specific presentation
  code in the service layer.
- `evals/consistency.py` and `evals/adjudicate.py` from the shipped package — move to
  `scripts/`; they call `OpenAI()` directly, bypassing `OpenAIClient`.
- Guards with negative net value per STATUS (`dropped_concepts`, `opaque_grouping_keys`)
  once structured outputs land; keep `restricted_request` and `dropped_literals`.
- App-level rate-limit loop and `response_format` fallback in `OpenAIClient` for
  `provider == "openai"`.

**Merge**
- `engine/execute.py`, `postgres.py`, `databricks.py` → one
  `run_with_policy(backend, compiled, opts)` holding timeout/row-cap/audit; each backend
  a ~20-line `Backend` protocol (`connect`, `execute(sql) -> (cols, rows)`, `interrupt`).
- `kernel/joins.approved_path` and `resolve_joins` BFS → one
  `shortest_join_path(catalog, a, b) -> list[JoinKey] | Ambiguous | Unreachable`.
- `kernel/joins.fan_out_errors` and `sql_validate._check_fan_out` → one
  `grain_check(base_table, joins, aggregates)`.
- `LogicalPlan.to_json` canonicalization and `compile._hash_plan` → one `canonical_json(plan)`.
- Planner selection: pick **one** path. STATUS says SQL path is +16 pts on Spider at the
  same wrong rate; the LQP argument ("model never writes SQL") is already false in the
  product. Keep LQP only if `explain.py`'s deterministic English is required.

**Replace**
- JSON-shape prose in `SYSTEM_PROMPT` → `LogicalPlan.model_json_schema()` via structured outputs.
- Per-request construction → startup singletons.
- `clarify.code_from_guard_message` string matching → guards return `(code, message)`.
- `metrics_for_catalog(c)` (`return list(c.metrics)`) and `metric_tables` via
  `_parse_agg(f"{m}:_")` → direct attribute access and a real parser.

1. **Pin execution to the reviewed plan** (C1). Add `/ask/execute` taking `plan`/`sql` +
   `plan_hash`, re-validate without an LLM call, 409 on mismatch.
